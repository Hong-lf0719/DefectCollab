设计要点

  • 三角色分工清晰：测试负责质量门禁（复测/关闭/重开）、跟踪质量与回归；产品负责决策（确认/拒绝/优先级/指派）；开发负责修复（认领/修复/阻塞）。三方均可登记缺陷（测试为主提交方）。
  • 权限控制到字段：优先级/严重程度/指派仅产品可改，阻塞仅开发可标，关闭/重开仅测试——后端 can_edit_field/can_transition 双重校验。
  • 共同进度：仪表盘聚合状态/优先级/处理人分布 + 三角色各自的待办队列，三方看同一份事实。
  • 实时监控：活动流每 5s 轮询刷新，状态变更即时可见。
  • 可追溯：每次状态流转/字段变更/评论/系统告警都写 history（谁·角色·时间·前后值）。
  • 可拓展：角色/状态/流转/阈值全在 state_machine.py，前端按 /api/meta 渲染，新增状态只改一处。
  • 保底机制：SLA 超时（验证48h/修复72h）、重开超上限、已确认未指派、开发阻塞——自动计算并预警，首次触发写入时间线，避免缺陷“石沉大海”。

① 我做这个系统，是要解决什么

缺陷管理最容易坏在「不是没人管，而是没人知道该谁管」。我把真实协作里最常见的四个坑作为设计目标——每一条都对应下面一个机制，而不是先做页面再想功能。

1缺陷石沉大海

现象：提了没人跟，几天后才发现还躺在那。对应机制：SLA 保底预警——超时自动算风险并置顶，不等人想起来。

2责任边界模糊

现象：「这不是我的问题」扯皮。对应机制：三角色 + 状态机白名单——每个状态下「谁能做什么」写死在服务端，扯不动。

3信息散在聊天里

现象：群里口头对齐，事后查不到。对应机制：单一事实源 + 评论留痕——所有沟通沉淀在缺陷本身，换人接手也能看懂。

4改了什么无从追溯

现象：优先级悄悄被改，不知道是谁。对应机制：字段级变更审计——谁、什么角色、什么时候、从什么改成什么，全记。

② 四条设计原则（所有功能都从这四条推出来）

原状态机驱动，而不是「状态随便下拉」

状态不是一个可自由填写的字段，而是一个有向图：7 个状态、7 条合法流转，每条流转绑定唯一角色。前端看到的按钮是服务端算出来的，前端就算被篡改，后端 can_transition 也会拦。权限判断永远在服务端，前端只负责渲染。

原权限控制到字段，不只到页面

很多系统做到「这个页面谁能进」就停了。我这里下沉一层：同一个抽屉里，产品能改优先级、开发只能标阻塞。粒度到字段，才真正贴近分工。

原规则集中声明，而非散落 if-else

状态、流转、角色、字段权限、SLA 阈值全部声明在 state_machine.py 一处，前端通过 /api/meta 动态渲染。加一个状态只改一个字典，不用碰前端和业务代码。下面的权限矩阵就是从后端实时读出来渲染的，不是我手写的死表格。

原系统要主动兜底，不能只当记录本

被动记录没有价值。保底机制让系统自己发现问题：已确认却没人认领、修复超时、复测超时、反复重开——四种信号自动算成风险，在共同进度页置顶预警；首次触发还会以「保底机制」名义写进缺陷时间线，事后可查。

④ 保底机制：让缺陷不会石沉大海

险四种风险信号

① 已确认但未指派——产品确认了却没人认领，最容易漏；

⑤ 工程上的取舍（为什么这么做）

取SQLite + FastAPI，不上重中间件

缺陷协作是中等写入量、强一致性场景，SQLite 完全够用，换来的是零运维、单文件可迁移。需要换 PostgreSQL 时，只改数据访问层。

取前端零依赖原生 JS，独立文件组织

不引 React/Vue。页面交互复杂度（列表+抽屉+图表）撑得起原生实现，换来秒开、无构建、可直接部署。结构上 HTML / CSS / JS 分离（style.css / app.js），是标准的独立网站前端工程。这是「够用就好」的取舍，不是不会用框架。

取Meta 驱动渲染

前端启动先拉 /api/meta，用后端声明渲染状态筛选、优先级下拉、状态机图、角色分工、权限矩阵。规则和展示不重复定义，避免两处不一致的经典 bug。

取实时监控用 WebSocket 推送（轮询兜底）

缺陷变更后服务端经 /ws 主动广播，前端即时刷新；连接断开时自动回退 5 秒轮询，保证弱网下也不丢更新。比纯轮询更省流量、更接近真实协作。
